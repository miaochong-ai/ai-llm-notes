**结论先说：多轮对话的成本不是「每轮字数 × 轮数」，而是每条请求都把整段历史重发一次，累计输入 token 随轮数近似平方增长。** 我用 tiktoken 本地跑了一组 6 轮对话：每轮 252 字提问 + 448 字回答，6 轮累计输入 8253 token，而模型真正「产出」的只有 1596 token。也就是说，账单里八成以上花在你已经说过的话上。

## 场景：预算为什么总是估不准

做按量计费、每日额度、上下文裁剪时，最常见的三个估法都不准：

1. 按字数估 token。中文一个字约等于 0.6–0.7 token，但代码、JSON、英文混排时比例会跳。
2. 只算「本轮问 + 本轮答」。实际请求里还带着 system prompt、前几轮问答、工具定义。
3. 忽略 chat 结构开销。每条消息在请求里都有一层角色分隔的固定开销，几十条消息加起来不是小数。

估错的后果很实际：额度按「轮数」给，用户聊到第 5 轮就被限流；按「字数」报预算，月底账单超一倍。

## 做法一：先用本地分词把「字数」换成 token

```python
import tiktoken
enc = tiktoken.get_encoding("o200k_base")   # GPT-4o / GPT-4.1 / GPT-5 系列
print(len(enc.encode("订阅类商品在维护期内需要暂停下单入口")))
```

`o200k_base` 是 2024 年之后 OpenAI 主力模型用的编码，`cl100k_base` 是 GPT-4 / 3.5 时代的编码。**同一段中文，用 cl100k 数出来比 o200k 多五成**（实测 47 vs 31 token）。如果你的计费脚本还写死 cl100k，遇到新模型就会系统性高估。

## 做法二：把 chat 结构开销算进去

OpenAI cookbook 给的估算口径是：每条 message 约 3 token 的结构开销，每次请求再加 3 token 回执。按这个口径写函数：

```python
PER_MSG = 3
PRIMING = 3

def chat_tokens(enc, msgs):
    return sum(len(enc.encode(m["content"])) + PER_MSG for m in msgs) + PRIMING
```

它的意义不是精确到 1 token，而是让你在「要不要再塞一条工具定义」这种决策上有数：一条 300 token 的工具定义，每轮都重发，6 轮就是 1800 token。

## 做法三：压缩历史，比换模型更省钱

滑动窗口和摘要压缩的原理是：把前几轮压成一段 200 字以内的结论，替换掉原始对话。我实测了同样 6 轮、第 4 轮起压缩前 3 轮的效果，直接看数据。

## 实测结果

环境：Python 3.13.18 / tiktoken 0.14.0，2026-11-23 本地运行，两个样本各 1 段文本（非批量统计）。

分词比（同义内容）：

```
中文-方案说明: chars=46 o200k=31 cl100k=47 每汉字token(o200k)=0.67
英文-同义:     chars=140 o200k=26 cl100k=26
```

6 轮对话（每轮 user 252 字、assistant 448 字，历史全量重发）：

```
turn1: prompt=203   out=266  累计输入=203
turn3: prompt=1141  out=266  累计输入=2016
turn6: prompt=2548  out=266  累计输入=8253
压缩后累计输入=4446  节省=3807 (46%)
```

三个可以直接用的结论：

- **第 6 轮单次 prompt 是第 1 轮的 12.5 倍**（2548 vs 203），增长来自历史，不是你这次问得更长。
- **输出只占 19%**（1596 / 8253）。想省钱先砍输入，换更便宜的模型对总账单影响有限。
- **压缩前 3 轮省 46% 的输入**，代价是丢失细节。适合「结论型」对话，不适合需要逐字引用原文的审稿、合同类场景。

## 坑与边界

- **编码要和模型对上。** 用错编码估出来的数会偏三到五成，这是我自己踩过的坑，别在计费脚本里写死一个编码。
- **缓存命中只对「完全相同的前缀」生效。** 官方对缓存命中的输入 token 有折扣，具体比例以官方定价页为准（https://platform.openai.com/docs/pricing，截至 2026-11）。所以把稳定内容（system、工具定义）放前面、把变化的用户输入放后面，命中率才高；顺序一乱，缓存全废。
- **tiktoken 是估算，不是账单。** 请求返回的 `usage` 字段才是结算口径，含工具调用、图片与特殊 token 的差异。对账时以 usage 为准，tiktoken 只用来做预算和上限控制。
- **不要把「轮数」当额度单位。** 轮数对应的成本跨度太大（第 1 轮 203 token，第 6 轮 2548 token），按轮数限流对短对话用户太宽松、对长对话用户太苛刻。按 token 限流才公平。
